## 当前实际问题

- 1440 × 1000：导航和主要内容之间有约 200 px 的无信息空白；左栏较窄，正文和两颗主要按钮连续换行。真实演示画面清楚，是应该保留的证明。
- 390 × 844：应用窗口在产品说明之前；初次访客先看到缩小的复杂桌面界面，首屏的价值主张、平台下载靠后。移动端章节导航被 CSS 隐藏。
- 主要内容采用六个互斥文字块和约五屏的 sticky 滚动。固定价值主张和访问具体功能都依赖滚动进度；需要检查可见性、焦点与直接导航，而不是让动画控制阅读。
- 实测主下载按钮前景是 `rgb(27,33,24)`，背景 `rgb(47,107,79)`；通用 `.lp a { color: inherit }` 的优先级盖过 `.lp-btn-primary`。导航按钮仍是白字。修复要覆盖真实链接元素，不能只改 token。
- “下载已经开始”的 Star 提示只根据点击触发，无法确认下载成功；当 API 不可用、跳转 GitHub Releases 时仍会声称已下载。应删除打断式索取 Star，或只表达真实动作。
- “数据只在两个地方”“ZeppBridge 服务器不存在”没有区分本地健康档案、授权回调/错误报告/更新服务，以及用户主动交给外部 AI 的文件。按实际数据用途说明边界比绝对措辞可信。
- 当前落地页嵌入开发中的 v3 演示，但 `/api/release` 明确只选公开稳定发行（拒绝 prerelease）。演示与下载必须标清渠道关系，不能让访客以为会下载当前未公开 beta。

## 现有价值

保留暖纸色/橄榄绿与深色主题、MiSans、本地优先与开源定位、样本缺失约定、十种语言、真实示例数据应用和官方稳定下载回退。修改限于落地页及必要验证；其他正在变化的桌面应用文件由其原任务拥有。

桌面与手机宽度、中英文与所有懒加载语言、亮暗主题、减少动态、键盘章节选择/直接导航、演示接管和退出、外部提交边界、下载 API 正常/失败、真实生产构建预览。此任务不部署，不构建或替换桌面 EXE，不读写真实库。
